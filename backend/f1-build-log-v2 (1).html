Step 09Errors ×3
Resolved 3 settings.py mistakes
① config() value vs name — config('django-insecure-...') should be config('SECRET_KEY'). The argument is the variable name to look up, not the value itself.

② cast=True vs cast=bool — True is a value, bool is a type. config('DEBUG', cast=bool) correctly converts the string "True" from .env to Python True.

③ venv not activated — Running manage.py without (venv) active causes ModuleNotFoundError. Always check for (venv) prefix in terminal before running any Django command.
All Resolved

02 — Root Cause Analysis

THE SUPABASE PROBLEM

Why connecting to Supabase from Nigeria required the Session pooler — and what each connection type means.

Direct Connection
db.ref.supabase.co : 5432
Resolves to IPv6 only on Nigerian networks. psycopg2 on Windows cannot connect over IPv6. DNS resolves fine but connection times out or fails. Not usable without IPv4.
Transaction Pooler
aws-0-eu-west-1.pooler.supabase.com : 6543
Stateless pooler for serverless/short-lived connections. Requires postgres.ref username format. Not ideal for Django which uses persistent connections. Was causing Tenant or user not found errors.
Session Pooler ✓ Solution
aws-1-eu-west-1.pooler.supabase.com : 5432
Supabase's recommended option for IPv4 networks. Uses port 5432 (same as direct). Resolves to IPv4. Requires postgres.ref username. This is what finally worked.
Key Lesson
aws-0 vs aws-1 matters
Transaction pooler is aws-0-region. Session pooler is aws-1-region. Same region (eu-west-1), different load balancer. One character difference, completely different behavior.

AWS RDS MIGRATION

Supabase is staying for now. This migration is planned as a standalone exercise between Phase 2 and Phase 3 — primary motivation is AWS experience, not a technical requirement.

P2→P3
Planned Timing
After Phase 2 endpoints are stable. Before Phase 3 begins. Clean checkpoint with no feature work in flight.
~2
Days Estimated
RDS setup + security group config + connectivity test + .env swap + endpoint verification.
0
Code Changes
settings.py stays identical. Only .env values change — host, port, user, password. Same psycopg2 driver.
01
Create RDS instance in AWS console
PostgreSQL engine. Choose instance type (db.t3.micro is fine for this stage). Note the endpoint, port, and credentials.
Migration
02
Configure VPC and security group
Most critical step. Set inbound rule on port 5432 to allow your IP. Public accessibility setting determines whether you can connect from local machine — same IPv4 concern as Supabase.
Migration
03
Swap .env values
Replace SUPABASE_DB_* keys with RDS endpoint, default port 5432, and credentials. settings.py untouched.
Migration
04
Run migrations against RDS
python manage.py migrate — recreates all Django built-in tables on the new database. Same command as Supabase setup.
Migration
05
Verify all Phase 2 endpoints
Hit every API route and confirm JSON responses match what they returned on Supabase. Data should be identical — same Django, same FastF1, different database backend.
Migration
Why Not Now
Don't switch mid-phase
Phase 2 API work is in progress. Infrastructure changes mid-feature break momentum and make debugging harder — you won't know if a bug is in the code or the new database. Finish Phase 2 first.
Why At All
Experience, not necessity
Supabase is working fine. The migration is purely for AWS exposure — VPC config, security groups, IAM basics, RDS console. These concepts appear in nearly every backend role at scale and are more transferable than Supabase-specific knowledge.
Key Risk
IPv4 connectivity from Nigeria
Same issue as Supabase. RDS public accessibility must be enabled and the security group inbound rule must allow port 5432 from your IP. Verify this first before spending time on anything else.
CV Value
Concrete, describable outcome
"Migrated PostgreSQL backend from Supabase to AWS RDS — configured VPC, subnet groups, and security groups. Zero application code changes required." That's a clean bullet point.
07 - Testing Workflow

TEST COMMAND REFERENCE

The test suite is split into unit and integration packages. Unit tests run fast with mocks. Integration tests hit live APIs and are skipped unless explicitly enabled with an environment flag.

Unit
Default in CI
Mocked endpoint tests only. Fast and deterministic.
Integration
Opt-In
Live FastF1 and standings API checks. Enable with RUN_INTEGRATION_TESTS=1.
Both
Pre-Release
Runs everything. Integration remains skipped unless flag is enabled.
Windows CMDCommands
.\venv\Scripts\python manage.py test api.tests.unit --keepdb .\venv\Scripts\python manage.py test api.tests.integration --keepdb set RUN_INTEGRATION_TESTS=1 && .\venv\Scripts\python manage.py test api.tests.integration --keepdb .\venv\Scripts\python manage.py test api.tests --keepdb set RUN_INTEGRATION_TESTS=1 && .\venv\Scripts\python manage.py test api.tests --keepdb
