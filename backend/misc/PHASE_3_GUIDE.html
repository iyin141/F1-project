PHASE 3.1: Next.js Project Setup & Environment

Goal

Initialize a Next.js project as a sibling folder to backend/, configure environment variables, and establish the foundation for API communication.

Overview

Next.js is a React framework that provides:

  • App Router - file-based routing (files in app/ folder become pages)
  • Server Components - render on server by default (better for data fetching)
  • Client Components - render in browser (for interactivity)
  • Built-in API proxy - rewrite requests to backend via next.config.js

For Phase 3.1, we're setting up the project structure, environment variables, and API client layer.

Key Setup Steps (Conceptual)

1. Create Next.js project in frontend/ folder

  • Use create-next-app CLI with TypeScript, ESLint, Tailwind CSS enabled
  • App Router selected (not Pages Router)
  • Import alias configured (@/ for src)

2. Configure Environment Variables

  • Create .env.local file (local dev secrets, Git-ignored)
  • Set NEXT_PUBLIC_API_BASE_URL=http://localhost:8000/api (during dev)
  • Reason: NEXT_PUBLIC_ prefix exposes variable to browser (needed for client-side API calls)

3. Set Up API Client Layer

  • Create lib/api/client.ts - Axios instance with:
    • Base URL from environment variable
    • Default headers (JSON content-type)
    • Error interceptor (catch 500, 404, network errors)
    • Request/response interceptor (log calls for debugging)
  • Create lib/api/services.ts - Schedule-specific service
    • getSeasonSchedule(year: number) function
    • Fetches from GET /races/{year}/
    • Returns typed response (RaceSchedule[] type)
    • Throws on error (caught by component)

4. TypeScript Types for API Responses

  • Define types/api.ts or add to lib/api/services.ts:
    • Race type with fields: round, name, date, location, country
    • ScheduleResponse type (array of Race)
  • Why: IDE autocomplete, compile-time type safety, self-documentation

5. Tailwind CSS Configuration

  • tailwind.config.ts - add theme colors (F1 branding: red, white)
  • globals.css - import Tailwind utilities, base styles
  • Reason: utility-first CSS framework, minimal custom CSS needed

PHASE 3.2: API Client & Error Handling Layer

Goal

Build a reusable HTTP client that communicates with the Django backend with consistent error handling.

Key Concepts

Axios Instance (lib/api/client.ts)

  • Centralized HTTP client instead of fetch()
  • Single place to configure base URL, headers, error handling
  • Request/Response interceptors for logging, auth, retries (future-proof)

Service Module (lib/api/services.ts)

  • Pure functions that use the Axios client
  • One function per API endpoint (or grouping)
  • Type-safe: takes typed params, returns typed data or throws
  • No React components here - pure business logic

Error Strategy

  • Network errors (connection refused) → show "Cannot reach backend" message
  • 4xx errors (400 invalid year) → show user-friendly message from response
  • 5xx errors (500 server crash) → show generic "Server error, try again later"
  • Timeout (request takes >10s) → show "Request timed out"

Structure Sketch

lib/api/client.ts:
  - Create axios instance
  - Set NEXT_PUBLIC_API_BASE_URL
  - Add error interceptor: catch errors, log, re-throw with context
  - Export the instance

lib/api/services.ts:
  - Import axios instance
  - Define RaceSchedule type (round, name, date, location, country)
  - Function: getSeasonSchedule(year: number)
    - Call: GET /races/{year}/
    - Return: typed responses array
    - Throw on error
  - Export types and functions

Error Handling Flow

  1. Component calls getSeasonSchedule(2024)
  2. Service makes HTTP GET to http://localhost:8000/api/races/2024/
  3. If success (200): return parsed, typed response
  4. If error (any): interceptor logs it, throws with message
  5. Component catches error, shows user message + retry button

PHASE 3.3: Schedule Page Structure & Components

Goal

Build the races/page.tsx (Schedule page) and break it down into composable components.

Page Strategy

Server vs. Client Components

  • app/races/page.tsx - Server Component (default in Next.js 13+)
    • Fetches data on server (no API key exposed to browser)
    • Passes data to client components
    • Lighter HTML sent to browser
  • YearSelector.tsx - Client Component
    • User clicks year dropdown
    • Sends to parent as callback
    • Parent re-fetches data server-side
  • RaceCard.tsx - Client Component (optional for now, or Server Component)
    • Displays one race's info
    • Styled card with name, date, location
    • Maybe link to race details (Phase 3.2+)

Component Breakdown

1. ScheduleContainer.tsx (Server Component)

  • Receives races prop (pre-fetched data)
  • Receives year prop (current selected year)
  • Shows title: "2024 F1 Season Schedule"
  • Renders grid of RaceCard components
  • Handles empty state: "No races found for {year}"

2. RaceCard.tsx (Client Component)

  • Input: single Race object
  • Displays: Round number, Race name, Date (formatted), Location, Country flag (emoji or image)
  • Styling: Tailwind card (border, shadow, hover effect)
  • Interactive: Click to navigate to race details (Phase 3.2+)

3. YearSelector.tsx (Client Component)

  • Input: currentYear, onYearChange callback
  • Displays: Dropdown with years 2020-2026 (or currently available)
  • On select: call onYearChange(2024) → triggers server-side re-fetch
  • Styling: Tailwind button/dropdown

4. page.tsx (app/races/page.tsx) - Server Component, orchestrator

  • Read query param: ?year=2024 (defaults to current year)
  • Call getSeasonSchedule(year) (from Phase 3.2)
  • Pass data to ScheduleContainer
  • Pass year & handler to YearSelector
  • Show loading skeleton while fetching (optional for MVP)
  • Show error message if fetch fails

Data Flow

User opens http://localhost:3000/races?year=2024 ↓ app/races/page.tsx (Server Component) ├─ Read query param: year=2024 ├─ Call getSeasonSchedule(2024) ├─ Receive races array └─ Render JSX with: ├─ YearSelector (year=2024, onYearChange callback) └─ ScheduleContainer (races=[], year=2024) └─ Render map(races → RaceCard)

Page Layout Hierarchy

app/layout.tsx (Root Layout)
  - Header (F1 logo, navigation)
  - Navigation menu (future: links to Standings, Race Details)
  - <main> with children
  - Footer (future)

app/races/page.tsx
  - YearSelector component
  - ScheduleContainer component
    - RaceCard × 24 (typical season)

PHASE 3.4: Running & Testing the MVP

Goal

Get the frontend running locally and verify API communication.

Setup Steps (Conceptual)

1. Install Dependencies

  • Run: npm install (installs packages from next.js template)
  • Packages included: React, Next.js, Tailwind CSS, ESLint, TypeScript

2. Start Development Server

  • Run: npm run dev
  • Starts on http://localhost:3000 by default
  • Next.js file watcher automatically restarts on changes

3. Manual Testing - Schedule Page

  • Browser: http://localhost:3000/races?year=2024
  • Expected: Page loads with 24 race cards
  • Each card shows: Round number, name, date, location, country
  • DevTools Network tab: verify GET http://localhost:8000/api/races/2024/ is called

4. Year Selector Testing

  • Click dropdown, select year 2023
  • Browser URL changes to ?year=2023
  • Page re-fetches: GET http://localhost:8000/api/races/2023/
  • 24 races (or different count if 2023 had changes) display

5. Error Testing

  • Stop Django backend (Ctrl+C in backend terminal)
  • Refresh page in browser
  • Expected: "Cannot reach backend" or "Error loading schedule" message
  • Start backend again, refresh, verify recovery

6. Browser DevTools

  • Network tab: trace requests to localhost:8000/api/*
  • Console: check for errors (should be clean)
  • React DevTools: inspect component tree, props
