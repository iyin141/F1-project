# Real-data API test, 2026-11-24

This is the first HTTP test of the v2 backend against real data. A future VM run can compare against it.

## Setup

- Stack: `v2/integration` at commit b8f2fa5, production compose, nginx on port 8030, amd64 Docker Desktop.
- Not started: `worker-rag` (its image build is blocked on this network) and the `ml` profile.
- Data: Neon production, copied with `pg_dump`, which only reads Neon. It was restored into the stack's Postgres, then migrated.
- Requests: through nginx, with an internal API key. Email and proxy credentials were left empty on purpose, so no mail could be sent.
- Test race: 2026 round 5, drivers NOR and VER.

## What the Neon data holds

- Driver telemetry only for 2026 R1 and R5, both race sessions.
- Race results for 3 seasons.
- 2,266 rows of lap analysis.
- `track_status_data` is empty, and there are no pit stops for R5.

So any feature needing more telemetry, track status, or qualifying sessions is limited by the data, not the code.

## Findings to fix

1. **The track-map build has no fallback after the session loads.**
   - `_load_session` falls back from Q to R only when loading raises an error.
   - In this run, FastF1 "loaded" but without laps or position data, so `build_from_session` raised `DataNotLoadedError`.
   - Fix: catch the build error per session and try the next one. Return a clear pending/failed message instead of a 37 s request.
   - It needs FastF1 live access to position data, so test it on the VM, which has a clean network.
2. **`track-map` and `track-status` answer 200 with a failed body after a long synchronous FastF1 load.** For a client this should be 202 pending or 503.
3. **The chaos circuit for 2026 R5 is `unknown`, so circuit features are empty.**
   - Run `link_circuit_keys` after the track map is built.
   - Check that the schedule's location names match the seed's aliases.
4. **The Neon migration script needs two fixes.**
   - It restored over a database that was already migrated, which conflicts on `django_content_type` and `auth_permission`. The correct order is: empty the `public` schema, `pg_restore`, then `migrate`.
   - Its row-count check flags tables that exist only in the stack (the v2 apps and the Django auth tables) as differences. Compare only the tables present in Neon.
   - It also restores Neon's own `neon_auth` schema, which should be excluded.
5. **Data gaps, not code bugs.** There's little stored telemetry (2 races), no track status, and no qualifying sessions. Run the ingestion and seed commands on the VM before judging the v2 features.
